природы, тишины и чистого океана. Мадейра — первый остров Атлантиды, где это

приманка для трафика. Всё работает на одну цель: стать главным источником
для тех, кто ищет редкий отдых в Атлантике.

**Мы не каталог отелей. Мы — издатель редких мест.**

- Атлантида / последний остров

## 4. СОЗДАНИЕ HTML-СТРАНИЦ

### Правила

1. **Каждая страница = один HTML-файл** в корне `madeirabook-site/`.
2. **Имя файла:** `[city]-to-madeira.html` или `[topic].html` (латиница, дефисы).
3. **Структура:** Hero → блоки → CTA → футер.
4. **Tailwind:** подключается через CDN (`<script src="https://cdn.tailwindcss.com"></script>`).
5. **Картинки:** лежат в `images/`, имена в формате `madeira-[тема]-[номер].jpg`.
6. **Alt-теги:** обязательно на русском/английском с ключевыми словами.
7. **Schema.org:** для каждой страницы — `FAQPage` + `Article` + `ImageObject`.
8. **Визуальный якорь:** каждая страница имеет ровно один — карту, круг, график или before/after.

### Обязательная структура страницы

```html
<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>...</title>
  <meta name="description" content="...">
  <script src="https://cdn.tailwindcss.com"></script>
  <!-- Schema.org -->
</head>
<body>
  <main>
    <section>Hero</section>
    <section>Основной контент</section>
    <section>Визуальный якорь</section>
    <section>CTA → Забронировать с −10%</section>
  </main>
  <footer>...</footer>
</body>
</html>
```

### Чек-лист перед деплоем

- [ ] Мета-теги (`title`, `description`)
- [ ] Schema.org (`FAQPage`, `Article`)
- [ ] Alt-теги на всех картинках
- [ ] Внутренние ссылки (на главную, на бронь)
- [ ] Мобильная версия (проверить в Chrome DevTools)
- [ ] Визуальный якорь (карта / график / круг)
- [ ] CTA в конце страницы

## 5. SEO + GEO: ПРАВИЛА ОПТИМИЗАЦИИ

### SEO (Google)

- **Прямые ответы** в первых абзацах («Перелёт Лиссабон → Фуншал: 1ч 45мин, 20 рейсов в день»).
- **Таблицы и цифры** — Google любит конкретику.
- **FAQ-формат** — вопросы как в поиске.
- **Внутренняя перелинковка** — каждая страница ссылается на 2–3 другие.
- **sitemap.xml** — обновлять при добавлении страниц.

### GEO (AI Search — ChatGPT, Perplexity, Claude)

**Отличие от SEO:** AI цитирует **конкретику**, а не «сочинения». Твоя страница — справочник, не статья.

- **`llms.txt`** в корне сайта.
- **Schema.org `FlightOffer`, `FAQPage`, `VacationRental`**.
- **Прямые ответы в формате «вопрос-ответ»**.
- **Никаких литературных текстов** — только факты, цифры, структура.

### Почему HTML > Tilda для индексации

1. **Скорость:** Edge CDN Vercel отдаёт HTML за миллисекунды. Tilda генерирует на лету.
2. **Чистота кода:** Боты читают семантический HTML. В Tilda — куча `div.t123`.
3. **GEO:** AI легко «выдёргивает» факты из чистого HTML.
4. **Минимализм:** 4 сущности вместо 6.

## 11. ФОРМЫ И СБОР EMAIL (БЕЗ TILDA И FORMSPREE)

### Схема

```
Frontend (форма)
   ↓ POST /api/subscribe
Backend (madeirabook-core)
   ↓
Neon (таблица subscribers)
   ↓
Resend (письмо с PDF)
   ↓
Telegram-бот (уведомление тебе)
```

### Таблица `subscribers` в Neon

```sql
CREATE TABLE subscribers (
  id SERIAL PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  source TEXT,
  telegram_id BIGINT,
  created_at TIMESTAMP DEFAULT NOW()
);
```

### Эндпоинт `/api/subscribe` (madeirabook-core)

- Принимает `{ email, source }`.
- Валидирует через zod.
- INSERT INTO subscribers (ON CONFLICT DO NOTHING).
- Отправляет письмо через Resend (с PDF).
- Отправляет уведомление тебе в Telegram.
- Возвращает `{ ok: true }`.

### Преимущества

- **Своя база** — не теряется.
- **Нет зависимости** от сторонних сервисов.
- **В рамках архитектуры** — 4 сущности вместо 6.
- **Дешевле** — Resend бесплатно до 100 писем/день.

## 16. TELEGRAM MINI APP (TMA)

**Концепция:** TMA — это веб-интерфейс (React + Vite), который переиспользует Express-бэкенд `madeirabook-core` и его сервисы. Бот `@Madeirabookbot` — только точка входа. Webhook, не polling. Аутентификация через `initData`.

### Схема

```
Telegram → @Madeirabookbot → web_app URL → TMA (React)
                                    ↓
                          Express backend (madeirabook-core)
                                    ↓
                          Neon / Stripe / Smoobu
```

### Два интерфейса

1. **Guest TMA** — для гостя (бронирование, возврат, гастро-гид).
2. **Owner TMA** — для владельца апартаментов (заезды, выплаты, загрузка).

---

### 16.1. GUEST TMA — дизайн

**Стиль:** минимализм, вертикально, крупная кнопка на всю ширину.

**Главный экран — ОДНА динамическая кнопка.** Меняется в зависимости от состояния гостя:

| Состояние гостя | Что показывает кнопка |
|---|---|
| Новичок | 📅 Забронировать сейчас — и получите −10% на следующий раз |
| Вернулся | 🎁 Забронировать с −10% — ваша персональная скидка |
| Есть бронь | 🔔 Детали заезда — через X дней |
| После заезда | ⭐ Оценить поездку 1–10 |

**Плюс тонкая ссылка внизу:** `🍷 Еда · Вино · Гид →`

**Логика −10% (повторная бронь):**
- Платформенная скидка, не per-property.
- Работает по всей сети Madeirabook.
- Владельцы подписываются через галочку в кабинете.
- В канале повторов видны только объекты подписавшихся.
- В обычном поиске (новичкам) видны все объекты.
- Скидка бессрочная (без таймера).
- Платформа отдаёт 10% из своей комиссии (12% → 2%).
- Владелец получает 88% как обычно.
- **Триггер:** наличие прошлой брони по `telegram_id`.

**Логика отзывов (после заезда):**
1. Экран «Как вам поездка?»
2. Оценка 1–10 (кнопки-кружки).
3. **Если ≥ 8** → кнопка «Оставить отзыв в Google».
4. **Если < 8** → текстовое поле для приватного фидбэка (Google-ссылка не показывается).
5. Владелец получает негативный фидбэк в Owner TMA — может исправить до публичного отзыва.

**Стиль:** информативный, цифры сразу видны. Сетка 2×2.

**4 плитки данных:**

## Сессия 26.09.2026 — Решения и модель

### Бизнес-модель (одним абзацем)

Madeirabook — не OTA и не PMS. Это клуб лояльности гостей + витрина доверия для владельцев.
Гость входит через мои ворота (сайт / бот / TMA). Бронь живёт во внешней системе
(Zeevou или Smoobu). Деньги через Stripe Connect идут напрямую владельцу — я беру
только комиссию. Владелец сам отвечает за налоги, заезд, коммуникацию. Моя роль —
бренд, маркетинг, память о госте и механизм возврата.

Магнит системы: владельцы конкурируют за возвратных гостей через скидку 10%.
Только я знаю, кто возвратный. Booking так не может.

### Моя зона ответственности

Я отвечаю за: бренд, маркетинг, коммуникацию, память о госте.
Я НЕ отвечаю за: деньги, налоги, календари, брони, платежи, операционные вопросы.

### Внешний контур — карта связей

ГОСТЬ (сайт / бот / TMA) -> madeirabook-core (ядро управления) -> Zeevou API, Smoobu API,
Stripe, Neon, Resend, 360dialog. ВЛАДЕЛЕЦ (TMA /owner) -> madeirabook-core.
Обратно: webhook от Stripe / Telegram / Zeevou / Smoobu.

Правило: всё идёт через core. TMA не общается с Zeevou/Smoobu напрямую.

### Три категории людей в системе

- Владельцы. Ключ: email. Связано: список ID его объектов (из Zeevou/Smoobu).
- Гости-новички. Ключ: Telegram ID. Связано: имя, телефон.
- Гости-бывалые. Ключ: Telegram ID + email. Связано: имя, телефон, ID заказов, ID объектов.

Владелец попадает в систему через Stripe Connect (email оттуда).
Гость опознаётся по Telegram ID; email появляется, когда он оставит его при брони.

### Что хранится в Neon (наш сейф)

- Профиль гостя: Telegram ID, email (если есть), имя, телефон
- Сегмент гостя: новичок / бывалый
- У каждого объекта: флаг «даёт 10% возвратным» (да/нет)
- История броней: ID заказов + ID объектов

Чего в Neon НЕ хранится:
- деньги, карты, календари, доступность, цены, сами брони (у внешних систем)
- связи «этот гость <-> этот владелец» (не нужны — скидка работает как общий бассейн)

Скидка 10% работает так: бывалый гость видит пересчёт цены у ЛЮБОГО объекта,
где стоит флаг «даёт 10%». Независимо от того, где он останавливался раньше.

### Правила работы (5 правил)

1. 1 проект = 1 папка = 1 репозиторий = 1 Vercel-проект. Имена совпадают.
2. Деплой только через git push. Никаких ручных vercel --prod. Vercel сам забирает из GitHub.
3. Один файл — источник правды: этот ARCHITECTURA.md.
4. Ничего лишнего в корне репозитория. Тесты — в scripts/, временное — в .gitignore.
5. Один проект — один язык. TMA: React+Vite, core: Express, сайт: статика.

### Правила работы с Neon (5 правил)

1. Схема БД — в репозитории (db/migrations/). Никто не меняет Neon напрямую без файла.
2. Перед изменением — бэкап. Neon делает автобэкапы, но проверяем и знаем.
3. Не удаляем таблицы и колонки. Помечаем deprecated_.
4. Одна таблица — одна ответственность. Понятные имена.
5. Секреты от базы — только в .env + Vercel env.

### Разница API и webhook

- API — мы стучимся к ним («дай список объектов», «создай бронь»).
- Webhook — они стучатся к нам («оплата прошла», «бронь создана»).
Оба нужны. У нас уже работают webhook от Stripe и Telegram.

### Цепочка деплоя

Mac -> git commit -> git push -> GitHub -> Vercel сам забирает -> build -> deploy -> прод.
Vercel не получает push напрямую — он подписан на GitHub и сам забирает изменения.
При поломке: Vercel Instant Rollback (скорая) -> правка в GitHub -> push (лечение).

### Правило зеркала в GitHub

Obsidian — источник правды. GitHub — зеркало для чтения.
После каждой сессии копируем свежую версию этого файла в репозиторий madeirabook
в папку docs/ (docs/ARCHITECTURA.md) и пушим.

Правило: НИКОГДА не редактировать копию в git напрямую. Правки — только здесь,

**Правильный canonical string (6 строк через \n):**

    <HTTP_METHOD>
    <PATH>
    <QUERY_STRING>
    <X-TIMESTAMP>
    <X-NONCE>
    <SHA256_HEX_OF_BODY>

Пример для GET /api/apartments без тела:

    GET
    /api/apartments

    2026-09-17T19:58:36Z
    a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d
    e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855

**Ключевые правила:**
- SHA-256 body hash обязателен ВСЕГДА, даже для GET без тела.
  Пустое тело → хэш e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
- Timestamp: ISO 8601 UTC БЕЗ миллисекунд (YYYY-MM-DDTHH:MM:SSZ)
- Signature output: HMAC-SHA256 → Base64 (НЕ hex)
- Secret передавать как UTF-8 string, НЕ base64-decode
- Часы должны быть синхронизированы (5 мин drift → reject)
- Nonce: UUID v4, генерируется заново на каждый запрос

**Итог:** прошлый 401 был из-за отсутствия body hash в canonical string.

## 🚨 ПРАВИЛА АССИСТЕНТА (самоконтроль — не перекладывать на пользователя)

Эти правила ассистент проверяет САМ перед каждым неочевидным решением.
Если нарушает — говорит об этом вслух, не ждёт, пока пользователь поймает.

**1. Никаких ручных костылей, если есть API.**
Если данные можно получить автоматически — берём из источника, а не вписываем руками.
Пример ошибки: предложить вручную вписать названия объектов в Neon, когда есть Zeevou/Smoobu API.

**2. Никаких хардкодов, если есть параметр.**
Токены, ID, конфиги — только через .env и config. Никогда в коде.

**3. Всё через core.**
TMA и site не стучатся к внешним сервисам напрямую. Только через core.

**4. Не дублировать данные.**
Если данные живут во внешней системе — не копируем в Neon. Neon хранит только то,
что наше (память о госте, флаги, метаданные).

**5. В правильном репо.**
Перед правкой — проверить, что работаю в нужном из трёх репо (site/tma/core).
Смешивать нельзя.

**6. Не идти по быстрому пути в обход ARCHITECTURA.md.**
Если ARCHITECTURA.md говорит одно, а «так быстрее» — идём по ARCHITECTURA.md.
Отступление — только с явного разрешения пользователя, с записью причины в файл.

**7. Не терять незакрытые задачи.**
Перед закрытием сессии — сверить со Следующая_сессия.md. Ничего не удалять молча.

**8. Если не вижу весь файл — просить проскроллить, не гадать.**
Правило: не строить догадки о содержимом файла по куску. Попросить показать.

**9. Не ликовать рано.**
Пилот ≠ результат. Один работающий кусок ≠ готовый продукт. Оценки — честные,
без преувеличений. «Готово 40%» значит 40%, а не «почти всё».

**10. Если сомневаюсь — сказать об этом.**
Не делать вид, что всё понятно. Не выдумывать ответ. Если данных нет — попросить.

**Если я это нарушаю — пользователь имеет право сказать «ты ушёл в сторону» и остановить.**
Но по-хорошему я должен поймать себя сам.


**11. Ассистент не видит файлы на Mac пользователя.**
Ассистент видит ТОЛЬКО то, что пользователь показал: скриншот, копипаст, загруженный файл.
Правила работы с файлами:
- Файлы в GitHub → читаем через curl (ассистент даёт команду)
- Файлы только локально → пользователь загружает в чат ИЛИ показывает вывод cat/head
- Длинный вывод (100+ строк) → ассистент сам задаёт head -N / tail -N, не ждёт

**Если пользователь говорит «прочитай ARCHITECTURA.md» — ассистент НЕ делает вид, что прочитал.**
Он либо использует curl из GitHub, либо просит показать содержимое.


**12. Работа с выводом команд (чтобы не гонять скриншоты).**
- Ассистент САМ задаёт нужную длину: head -N, tail -N, sed -n 'X,Yp', grep -n.
- Не даёт "просто cat" файлов больше 40 строк.
- Если нужно больше 30 строк — прямо говорит: "скопируй текст из терминала, не скриншот".
- Никогда не просит "покажи весь терминал" — только вывод конкретной команды.
- Терминал сам по себе может быть большим — каждая команда выводит только свой результат.
